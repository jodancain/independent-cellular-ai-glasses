# 当前工程判断

**v0.1 公开讨论稿 · 2026-11-02**

本页给出项目选型判断与验证边界，不披露内部测试记录，也不宣称任何目标眼镜已完成全功能或量产验收。

## 1 先确认系统可控性 再冻结外形与芯片

优先确认可调试目标系统、BSP、驱动、系统服务和接口契约能够获得，之后再冻结硬件。应用能够运行、SDK 能够调用或某芯片算力足够，都不能单独证明项目可以长期维护。

采购评估应回答四个问题：

1. 项目方能否在目标系统中合法预装、授权和升级自有应用？
2. 摄像、音频、显示、蜂窝和电源管理是否有明确、可测试的接口？
3. 闭源依赖是否具备可持续的授权、更新和替代路径？
4. 不依赖供应商消费级账号或云服务时，设备能否继续工作？

## 2 应用验证与整机验收分开

手机或模拟器上的交互、功能和稳定性测试，只能支持对应应用层的判断，不能替代眼镜的鉴权、摄像、音频、HUD、蜂窝及功耗测试。

系统服务可能依赖目标固件、平台签名、共享 UID、私有 ABI 或硬件 HAL。不能假设将 APK 或固件组件复制到通用模拟器即可运行，也不能把改包重签当成获取系统权限的方案。供应商应提供合法、可操作的系统集成与签名流程；不要求将生产私钥交给应用开发者。

对摄像和音频，必须验证实际参数以及停止、取消、异常退出和重连后的资源释放。对显示，接口接入不等于已经正确显示。对稳定性，短时无失败不等于无泄漏或长期可靠，必须观察资源趋势和异常恢复。

## 3 用同一负载比较完整整机

蜂窝上行、摄像编码、拾音、显示与业务计算并发时，散热和续航决定可用性。芯片峰值算力、开发板空闲功耗或单一功能测试，不能推导出轻量整机可以全天持续视频。

至少分开测量待机、语音、间歇拍摄和持续远程视频，并在强弱信号条件下报告数据。电池、结构、天线、显示和系统策略需一起评估。

建议优先让供应商对 W527 与 W5 系列加蜂窝提交完整方案，再与其成熟替代方案比较。RV1126B 等摄像平台可用于功能原型，但不能只凭开发资料齐全就判断其适合轻量眼镜。[芯片对比](chips.md)保留了各路线的证据与限制。

## 4 Linux 与 Android 均保留

Linux 可用于轻量系统方案，但须确认驱动与媒体栈、交互开发成本、应用迁移和维护能力。Android 可降低部分应用迁移成本，但资源消耗、系统权限、平台签名和升级控制必须实际交付。

不凭操作系统名称决定优劣。建议 RAM 和存储档位只是询价起点，最终配置应由业务并发、资源余量、功耗与可获得的 BSP 质量决定。

## 5 开源参考用于判断资料成熟度

| 参考项目 | 可借鉴方向 | 不能据此认定 |
| --- | --- | --- |
| Frame | 眼镜固件、API 与开发资料 | 已具备本项目所需的独立蜂窝整机能力 |
| Halo | Zephyr、Alif Balletto、Lua、BLE 与 OTA 的接口和更新设计 | 等同于 ARM 应用平台加蜂窝方案 |
| OpenSource Ai Glasses | Linux 摄像、RTSP、BLE 音频及可选显示的功能原型 | 已完成轻量化、低功耗和量产验证 |
| MentraOS | 应用生态与手机协同架构 | 可直接作为本项目的独立眼镜操作系统 |

项目链接见[公开来源 S13 至 S16](sources.md#s13)。开源仓库数量不等于量产可控，部分代码公开也不意味着芯片 BSP、驱动及全部第三方依赖完整开源。

供应商应说明实际采用的代码版本、许可证、维护者和与交付硬件的对应关系。对没有完整公开证据的能力，使用“待确认”或“待验证”，不要写成已经支持。
