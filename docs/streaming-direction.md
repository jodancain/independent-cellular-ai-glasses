# 串流终端方向：Quest 级体验的 AR 眼镜版

**v0.4 方向稿 · 2026-11-03 · 来源核验日期 2026-11-03**

本页把“自研眼镜”的目标整理成一套可评审的技术路线：**联网后靠网络获得 Quest 级串流体验；通过投屏转化兼容尽量多的软件；与人眼看到的真实画面交互；断网时退化为手表级设备；视频通话与会议达到手机水平；具备强睡眠能力。**

> **证据边界**：本页区分三类内容——【公开资料】有来源链接的厂商或项目公开信息；【项目判断】本项目的推理与取舍；【设计目标】希望达到但尚未测量的指标。厂商宣传数字（如延迟、功耗）未经本项目复现，不能当作整机实测结果。本页不是冻结规格。

与 [开发需求](requirements.md) 的关系：需求文档面向“独立蜂窝 + 现场作业”的轻量眼镜；本页是另一条**串流终端**产品方向，两者共用“ARM 应用平台 + 自主软件 + 可维护 BSP + 不依赖手机独立联网”的边界。冲突时以需求文档的硬性边界为准。

## 0 一句话方案

**眼镜依赖网络而不是依赖手机：机身自带蜂窝和 Wi-Fi，联网时把重渲染交给任意主机（PC、手机、车机、云），眼镜只做“看清真实世界 + 定位追踪 + 低延迟解码 + 叠加显示 + 交互”；断网时只保留时间、拍照、录像、录音和极小本地程序，像一块戴在脸上的智能手表；不用时深度睡眠、秒级唤醒。**

### 0.1 需求方已确认的决定（2026-11-03）

| # | 问题 | 确认结果 | 对方案的影响 |
| --- | --- | --- | --- |
| 1 | 睡眠能力的含义 | 低功耗待机 + 快速唤醒 + 恢复原状态 | 第 5 节 |
| 2 | “特殊投屏算法”的理解 | 基本正确 | 第 4.1 节保留，细节可后续补充 |
| 3 | 5G 放线控模块还是做一体式 | **两种都要** | 机身内置蜂窝保证独立联网；线控模块提供大电池和更高带宽（第 1、6 节） |
| 4 | 主要外部主机 | **PC、手机、车机、云全部要** | 串流服务端做成多平台；主机发现与切换（第 3.4 节） |
| 5 | 是否需要 6DoF | **需要**，但不强调完整 VR 游戏；重点是 VR 级能力 + AR 效果，与人眼看到的画面交互 | 6DoF 追踪、空间锚定、手势交互成为基础能力（第 3 节） |

| 7 | 手表模式本地程序 | 由项目方结合资料定 | 内置程序清单 + 受限沙箱小程序接口（第 2.3 节） |
| 8 | 断网录制内容的上传 | **保留一个接口，由使用者自己选择** | 同步接口可选目标与方式，默认不上传，首次使用时让用户选（第 2.4 节） |
| 9 | 机身蜂窝最低要求 | **满足串流最低要求** | 定义串流最低网络指标，机身蜂窝按此选型（第 6.3 节） |
| 10 | 第一版样机范围 | **完全版** | 有线、Wi-Fi、蜂窝、6DoF、视频通话、手表模式全部进第一版样机（第 8 节） |
| 11 | 默认形态 | **默认无线** | 眼镜本体自带电池独立全功能；线控模块为可选配件（第 1 节） |
| 12 | 视频通话 | **拉满**：像正常手机视频电话、视频会议一样，包括投屏视频 | 新增视频通话与会议能力（第 3.7 节） |

### 0.2 相对 v0.2 的变化（v0.3）

| 变化 | v0.2 | v0.3 |
| --- | --- | --- |
| 联网方式 | 5G 只在线控模块里 | **机身内置低功耗蜂窝（RedCap / LTE）+ Wi-Fi**；线控模块可选，增加电池和高带宽 5G |

| 主机 | 主机待定 | PC、手机、车机、云四类全部支持 |

## 1 整体架构

```
       ┌─────────────────── 外部主机（重渲染，可任选）───────────────────┐
       │   PC / 笔记本   │   手机   │   车机   │   云端渲染 / 远程桌面      │
       │ 虚拟显示器驱动 + 编码器 + 自研串流服务（多平台统一协议）             │
       └──────┬────────────────┬──────────────────┬──────────────────────┘
    ① 有线 DP Alt / USB    ② Wi-Fi 7 / 6E       ③ 蜂窝（机身 RedCap / 模块 5G）
              │                │                  │
 ┌────────────▼────────────────▼──────────────────▼─────────────────────────┐
 │ 眼镜本体                                                                  │
 │  主处理器（联网全功能时工作）                                                │
 │   • 视频入口：DP 接收 或 硬件解码（H.265 / AV1，视芯片）                       │
 │   • 6DoF 追踪 + 手势 + 本地重投影：叠加内容锚定在真实世界                       │
 │   • 光学透视显示（AR 效果）：人眼直接看真实画面，虚拟内容叠加其上                │
 │   • Wi-Fi 7 + 机身蜂窝（RedCap / LTE，eSIM 或 SIM）                          │
 │  低功耗协处理器（始终在线）                                                  │
 │   • 断网手表模式：时间、拍照、录像、录音、极小本地程序                           │
 │   • 睡眠与唤醒：佩戴检测、IMU、按键、唤醒词                                    │
 │  小电池（保证手表模式与短时联网）                                            │
 └──────────────────────────────┬────────────────────────────────────────────┘
                                │ USB-C（供电 + 数据 + 视频）
                  ┌─────────────▼──────────────┐
                  │ 可选线控模块（扩展仓）        │
                  │ 大电池 + 高带宽 5G 模组       │
                  │ 可选：主机 USB-C 直通、存储    │
                  └────────────────────────────┘
```

【项目判断】**默认形态是无线**：眼镜本体靠自带电池、机身蜂窝和 Wi-Fi 独立完成全功能；线控模块只是可选配件，用于更长续航和更高带宽，不是使用前提。

为什么这样分：

- **依赖网络，不依赖手机**：机身自带蜂窝和 Wi-Fi，任何能上网的地方都能直接连云端或远程主机；手机只是主机之一。
- **机身蜂窝选低功耗档**：RedCap / LTE 足够做独立上网、消息、语音和中等码率云串流，功耗和发热比全功能 5G 小；需要高码率云串流、长时间户外使用时再接线控模块。
- **断网与睡眠交给协处理器**：主处理器、解码、追踪、显示都可以断电，只留协处理器跑手表模式，这是续航和睡眠能力的关键。
- **代价**：默认无线意味着机身要同时放蜂窝天线、两颗处理器、摄像头和足够的电池，重量、散热和成本上升；无线全功能（尤其是串流 + 视频通话并发）的续航是本方向最大的工程风险，必须用整机实测证明可接受。

## 2 两级功能模式

### 2.1 模式定义

| 模式 | 进入条件 | 保留功能 | 关闭功能 | 主要运行硬件 |
| --- | --- | --- | --- | --- |
| **全功能（联网）** | 有可用网络（Wi-Fi、机身蜂窝或模块 5G）并能连上主机或云 | 串流显示、6DoF 叠加交互、全部软件兼容、云端 AI、远程协作，以及手表模式全部功能 | — | 主处理器 + 协处理器 |
| **手表模式（断网）** | 无网络，或网络可用但所有主机和云都连不上 | 看时间、拍照、录像、录音、极小本地程序（如计时、备忘、离线提示卡、简单计算） | 串流、6DoF 叠加、软件兼容层、云 AI、其他全部功能 | 主要由协处理器；拍录像时按需唤醒摄像与编码 |

【项目判断】规则：

- 判断依据是**能不能连上服务**，不是“有没有连手机”。网络在但主机和云都不可达，也按断网处理。
- 断网期间拍的照片、录像、录音存在本地，恢复联网后自动上传或同步（用户可关闭）。
- 模式切换要无感：断网时当前串流画面淡出并提示“已切换到离线模式”；联网恢复后自动回到上次的主机和会话。
- 极小本地程序需要一个受限运行环境（例如脚本或小型应用容器），有内存、存储和权限上限，不能访问网络，不能长时间占用摄像头和麦克风。

### 2.2 手表模式的硬件要求

| 功能 | 要求 | 说明 |
| --- | --- | --- |
| 时间 | 实时时钟 + 低功耗显示刷新 | 显示可只点亮局部，低刷新 |
| 拍照 | 摄像头 + ISP | 协处理器需带 ISP，或能快速唤醒主处理器的 ISP |
| 录像 | 硬件 H.264 / H.265 编码 | 协处理器带编码最好；否则录像时唤醒主处理器 |
| 录音 | 麦克风 + 音频编码 | 协处理器即可 |
| 本地程序 | 小型运行时 | 内存以 MB 计，不要求跑完整操作系统应用 |
| 存储 | 本地闪存 | 容量按录像时长定 |

公开参照：STM32N657 为 M55 MCU，具 ISP 与 H.264 能力【公开资料】[S12](sources.md#s12)；W5+ Gen 1 配套 M55 协处理器【公开资料】[S2](sources.md#s2)；AR1+ Gen 1 有双 ISP【公开资料】[S18](sources.md#s18)。这些说明“协处理器负责低功耗功能、主处理器按需唤醒”的分工有现成芯片参照，但本项目所需的具体组合仍需供应商证明。

### 2.3 手表模式的本地程序（项目建议）

【项目判断】结合手表模式“只保留最小功能”的原则和协处理器的资源（内存以 MB 计），建议分两类：

**内置程序（出厂自带）**

| 程序 | 用途 | 依赖 |
| --- | --- | --- |
| 时钟 / 闹钟 / 计时 / 秒表 | 基本手表功能 | 实时时钟 |
| 相机 | 拍照、录像，查看最近几张 | 摄像头、ISP、编码 |
| 录音 / 语音备忘 | 录音、按时间列表回放 | 麦克风 |
| 提词卡 / 离线备忘 | 显示预先同步到本地的文字（清单、提词、操作步骤） | 本地存储 |
| 离线扫码 | 识别二维码并显示内容（不打开网址） | 摄像头 |
| 状态 | 电量、存储、网络状态、待同步数量 | — |

**第三方小程序（受限沙箱）**

- 运行在协处理器上的受限运行时：**WebAssembly（如 WAMR）或 Lua** 二选一或两者都支持。Halo 眼镜固件已采用 Lua 运行时承载设备端应用并支持 OTA【公开资料】[S14](sources.md#s14)；WAMR 是小体积的 WebAssembly 运行时【公开资料】[S29](sources.md#s29)。
- 限制：不能联网；内存、存储、CPU 时间有上限；摄像头和麦克风需用户每次确认；签名后才能安装；联网时通过主处理器下发和更新。
- 提供简单的显示、按键、触控、传感器和本地存储接口，让第三方能写计时、计数、清单、单位换算这类小工具。

### 2.4 离线内容同步接口（使用者选择）

需求方确认：断网时录制的照片、录像、录音，联网后是否上传、传到哪里，**保留一个接口，由使用者自己选择**。

【项目判断】设计：

- **默认不上传**。首次使用时让用户选择同步方式，之后可随时修改。
- 同步目标可选：不同步 / 局域网内的电脑或主机 / 用户自己的云存储（如 WebDAV、S3 兼容存储）/ 项目方云服务（如提供）。
- 同步方式可选：联网自动同步 / 仅 Wi-Fi 时自动同步 / 手动同步。
- 对外提供统一的**同步接口**（上传目标插件），第三方或企业可接自己的存储；接口只传用户选中的内容，记录同步日志，失败可重试。
- 本地内容在同步成功并经用户设置允许后才删除，避免断网录制内容丢失。

## 3 目标一：联网后的串流与真实画面交互

### 3.1 定位：VR 级能力，AR 效果

- 不追求完整 VR 游戏。重点是**和人眼看到的真实画面交互**：虚拟屏幕、信息卡、指引箭头、标注等稳定地“贴”在真实物体或空间位置上，用手势或注视来操作。
- 需要的能力：**6DoF 追踪**（头在空间里移动，叠加内容不漂移）、**空间锚定**（内容固定在真实位置）、**手势交互**、**平面 / 物体识别**（知道桌面、墙、设备在哪）。
- 显示走**光学透视**：人眼直接看真实世界，虚拟内容叠加其上。与摄像头透视的头显相比，真实画面没有延迟和画质损失，但叠加内容的亮度、对比度、视场受光学方案限制。

### 3.2 算力分工

| 环节 | 在哪里做 | 原因 |
| --- | --- | --- |
| 6DoF 追踪、手势、重投影 | **眼镜本地** | 对延迟极敏感，不能走网络 |
| 场景理解（平面、物体识别） | 本地轻量 + 主机 / 云重计算 | 结果可以慢一点，但需要持续更新 |
| 内容渲染（虚拟屏、3D 内容） | **主机或云** | 重计算，串流回眼镜 |
| 合成上屏 | 眼镜本地 | 用最新姿态把串流画面贴到正确位置 |

公开参照：AR2 Gen 1 采用多芯片分布式架构，把感知与低延迟环节留在眼镜端、重计算交给主机，并宣称 Wi-Fi 7 持续延迟 < 2 ms【公开资料】[S17](sources.md#s17)。

### 3.3 连接方式

| 模式 | 链路 | 体验定位 | 主要前提 |
| --- | --- | --- | --- |
| **A1 有线原始画面** | USB-C DP Alt Mode | 最低延迟、无压缩画质；固定场景“超强体验”上限 | 主机支持 DP 视频输出 |
| **A2 有线编码串流** | USB 3.x 数据通道 | 接近 A1，兼容没有 DP 输出的手机或主机 | 主机能硬件编码 |
| **B Wi-Fi 串流** | Wi-Fi 7 / 6E | 日常移动使用 | 主机有线接路由器或直连 |
| **C 蜂窝串流** | 机身 RedCap / 模块 5G | 离开主机时连云端或远程主机 | 运营商上行带宽与时延；云端渲染资源 |

公开参照：XR2（第一代，Quest 2 所用平台）5G 为可选集成【公开资料】[S19](sources.md#s19)；XREAL One 系列以 USB-C DP 输入并在眼镜端芯片做稳定与畸变校正，宣称约 3 ms【公开资料】[S20](sources.md#s20)；ALVR、WiVRn 是成熟的开源 PC → 一体机串流方案【公开资料】[S24](sources.md#s24)[S25](sources.md#s25)；Sunshine / Moonlight 支持 H.264、HEVC、AV1 平面串流【公开资料】[S26](sources.md#s26)。

### 3.4 四类主机统一接入

| 主机 | 接入方式 | 适合内容 | 说明 |
| --- | --- | --- | --- |
| PC / 笔记本 | 虚拟显示器驱动 + 串流服务；或 DP 有线 | 办公、开发、游戏、3D 内容 | 体验上限最高 |
| 手机 | 手机伴随服务（虚拟显示 + 编码）；或 DP 有线 | 手机应用、消息、导航 | 安卓与 iOS 能力不同，需分别评估 |
| 车机 | 车机侧串流服务或标准车机协议 | 导航、车辆信息、娱乐 | 行车安全需单独评估；不承诺驾驶中所有功能可用 |
| 云 | 云端渲染 + 蜂窝 / Wi-Fi 串流 | 离开本地主机时的全功能 | 时延和流量成本是主要约束 |

【项目判断】四类主机用**同一套串流协议**：会话握手带能力位、控制面与视频面分离、断线后自动回到上次主机；多个主机同时可用时按“有线 > 同局域网 > 云”的顺序优先。

### 3.5 延迟预算（设计目标，待实测）

| 环节 | A1 有线原始 | A2 有线编码 | B Wi-Fi 7 | C 蜂窝 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 编码 | 无 | ≤ 5 ms | ≤ 5 ms | ≤ 5 ms | 无 B 帧、切片编码、帧内刷新 |
| 传输 | 线路级 | ≤ 2 ms | ≤ 5 ms（p95） | 依网络，待测 | 蜂窝时延波动最大 |
| 解码 | 无 | ≤ 5 ms | ≤ 5 ms | ≤ 5 ms | 视芯片硬解能力 |
| 重投影 + 显示 | ≤ 5 ms | ≤ 5 ms | ≤ 5 ms | ≤ 5 ms | XREAL 宣称约 3 ms，未见独立实测 [S20](sources.md#s20) |
| **头动感知延迟** | 由本地追踪 + 重投影决定 | 同左 | 同左 | 同左 | 与网络延迟解耦，叠加内容不随网络抖动漂移 |

【项目判断】以上只是拆账用的设计目标。测试方法：高速相机或光电传感器测运动到光子；内容延迟测 p50 / p95（每组 ≥ 30 样本）；30 分钟连续运行看 p95 漂移和温度降频；蜂窝链路在强弱信号下分别测。

### 3.6 眼镜端能力要求（含视频通话）

| 能力 | 要求 | 状态 |
| --- | --- | --- |
| 6DoF 追踪 | 追踪摄像头 + IMU，本地运行 | 待选型 |
| 手势交互 | 本地手部追踪；注视交互可选 | 待选型 |
| 视频解码 | 硬件 H.265 必选；AV1 优先 | 依芯片核实 |
| DP 输入 | A1 模式需 DP 接收与显示桥接 | 待选型 |
| 显示 | 双目光学透视，1080p 级每眼起步，90–120 Hz 优先 | 待选型 |

| 机身蜂窝 | 满足串流最低网络要求（第 6.3 节），eSIM / SIM | 见第 6 节 |

### 3.7 视频通话与会议（拉满）

需求方确认：视频通话能力要拉满，包括投屏视频，**体验像正常手机视频电话、视频会议一样**。

**能力清单**

| 能力 | 做法 | 说明 |
| --- | --- | --- |
| 看对方 | 来电视频和会议画面作为虚拟屏锚定在空间里，可放大、多人宫格 | 走串流或本地解码 |
| 让对方看到我所见 | 眼镜前向摄像头作为通话摄像头（第一人称视角） | 适合远程协作、指导 |
| 让对方看到我本人 | 眼镜看不到佩戴者的脸：可切换为主机（手机、电脑）摄像头，或用虚拟形象 | 手机视频电话的“自拍画面”需要其他摄像头补位 |
| 共享画面 | 共享眼镜里的任一虚拟屏，或“真实画面 + 叠加内容”的合成画面 | 即“投屏视频” |
| 语音 | 波束成形麦克风 + 降噪 + 回声消除；静音、音量、耳机切换 | 开放式扬声器需防漏音 |
| 会议控制 | 接听、挂断、静音、切摄像头、举手，均可用手势、语音、按键完成 | — |

**三种通话接入方式（覆盖所有通话软件）**

| 方式 | 原理 | 覆盖 | 依据 |
| --- | --- | --- | --- |
| **V1 主机通话（兼容任何通话软件）** | 通话软件（微信、腾讯会议、Teams、Zoom 等）在 PC / 手机上运行，画面经 L0 虚拟显示器到眼镜；**眼镜摄像头和麦克风注册为主机的摄像头和麦克风** | 主机上能跑的全部通话软件，不需要软件适配 | 有线时眼镜可作为标准 USB 摄像头（UVC），Linux USB gadget 已有 UVC 功能实现【公开资料】[S30](sources.md#s30)；无线时由主机端虚拟摄像头 / 虚拟音频驱动接收 |
| **V2 眼镜独立通话** | 眼镜本地运行 WebRTC 通话客户端，直接经蜂窝或 Wi-Fi 通话，不需要主机 | 自研通话、远程协作、支持网页接入的会议 | WebRTC 为开源实时音视频框架【公开资料】[S31](sources.md#s31) |
| **V3 云端通话** | 通话软件在云端主机运行，经蜂窝串流到眼镜，眼镜摄像头和麦克风回传云端 | 离开本地主机时使用任意通话软件 | 依赖云主机与上行带宽 |

**设计目标（待实测）**

- 上行视频：1080p30 起，弱网自动降到 720p / 480p 保持流畅；音频优先于视频。
- 口到耳延迟和画面延迟按主流视频通话体验设定，具体阈值需结合实测基线确定。
- 通话与串流、6DoF 同时运行（解码 + 编码 + 追踪 + 蜂窝上行并发）时不降频、不过热——**这是整机最重的负载，必须作为验收主场景**。

**边界**：通话软件的端到端加密、账号、录制和第三方平台规则由各软件自身决定；V1 依赖主机能识别虚拟摄像头和虚拟麦克风，个别软件可能限制虚拟设备，需要按清单实测。

## 4 目标二：通过投屏转化算法兼容尽可能多的软件

### 4.1 “特殊投屏算法”（需求方确认：基本正确）

本项目所说的“特殊投屏算法”是以下组合，而不是某一种编码格式：

1. **主机侧渲染 + 视频 + 眼镜薄解码**：主机把内容画到一块虚拟画布，硬件编码后推给眼镜，眼镜只负责解码显示。
2. **串流纪律**：画面只保留最新一帧；同时只有一块数据在传；对端忙就丢帧而不是排队；回执逐项核对累计值；采集、编码、发送、解码、上屏分别计数，不把“已发送”当成“已显示”；断流时不显示花屏，等关键帧再恢复。
3. **ROI 局部放大**：在原始分辨率上先裁剪再缩放，让小屏也能看清局部内容。
4. **语义转化（主）+ 像素转化（兜底）**：能读到界面结构的应用，把内容重新排版成适合眼镜的卡片；读不到的再用画面捕获 + 裁剪 + 对比度适配。
5. **矢量与画面分开**：导航、字幕、状态等结构化数据单独传，由眼镜本地绘制，视频断开时仍能显示。

### 4.2 兼容分层

“兼容所有软件”最有效的做法不是逐个适配应用，而是**在操作系统显示层接入**：主机系统把眼镜当成一台显示器，任何能在这台显示器上显示的软件就自然兼容。

| 层 | 方法 | 覆盖范围 | 开源参考 | 边界 |
| --- | --- | --- | --- | --- |
| **L0 系统级虚拟显示器（主路）** | Windows 间接显示驱动（IddCx）；Linux 合成器 / Vulkan 层；Android VirtualDisplay / 屏幕捕获；Mac 系统扩展显示 | 所有桌面与普通应用，含多窗口、多屏 | Windows 虚拟显示驱动 [S27](sources.md#s27)；Breezy Desktop / XRLinuxDriver [S28](sources.md#s28) | DRM / HDCP 内容、安全窗口不可捕获；驱动签名与系统版本 |
| **L1 OpenXR / 空间应用** | 主机运行 OpenXR 运行时，眼镜作为显示与追踪端 | 空间应用、3D 内容 | ALVR、WiVRn [S24](sources.md#s24)[S25](sources.md#s25) | 光学透视下的显示效果与 VR 头显不同 |
| **L2 标准投屏 / 车机协议** | 眼镜作为接收端 | 手机生态的地图、音乐、语音 | 此前调研的车机接收端开源实现 | 协议授权、认证硬件和厂商条款须另行确认；本仓库不提供这类实现 |
| **L3 语义转化** | 读应用界面结构，重排为眼镜卡片 | 消息、文章、通知、列表 | 无障碍界面树读取思路 | 需用户授权；规则随应用更新失效；不做未经确认的自动操作 |
| **L4 像素转化** | 画面捕获 + ROI + 对比度适配 + 低码率编码 | L3 读不到的图片、小程序等 | 第 4.1 节串流纪律 | 低带宽兜底；受安全窗口限制 |

【项目判断】由于第 3 节以空间交互为核心，L0 的虚拟显示器在眼镜里不是固定在眼前，而是**作为虚拟屏幕锚定在真实空间**（如摆在桌面上方），可以多屏摆放。兼容率按“软件类别清单 + 实测通过率”衡量；DRM 保护内容、反作弊、仅限特定硬件的软件属于已知边界，不承诺可用，也不绕过。

### 4.3 自研串流协议要点

- 会话握手带能力位（分辨率、刷新率、编码格式、追踪模式），并做时钟同步。
- 控制面与视频面分离：视频断开时，按键、模式切换、诊断仍可走控制通道。
- 视频面“最新帧优先 + 关键帧恢复 + 自适应码率”；Wi-Fi 与蜂窝下按 p95 延迟动态降分辨率或帧率。
- 姿态数据单独上行，供主机做预测渲染。
- 诊断以 JSON 记录各环节计数与时间戳，不保存画面内容。

## 5 目标三：强睡眠能力（已确认：低功耗待机 + 快速唤醒）

### 5.1 分级功耗状态（设计目标）

| 状态 | 主处理器 | 协处理器 | 机身蜂窝 / Wi-Fi | 唤醒条件 | 设计目标 |
| --- | --- | --- | --- | --- | --- |
| S0 全功能 | 工作 | 工作 | 连接 | — | 由串流负载决定 |
| S0' 手表模式 | 关闭（拍录像时按需唤醒） | 工作 | 周期性尝试联网 | — | 续航以天计（待定） |
| S1 浅睡（摘下 / 熄屏） | 挂起，串流会话保持 | 工作 | 保持连接 | 戴上、触摸、按键 | 戴上后画面恢复 **≤ 1 s**（待实测） |
| S2 待机 | 挂起到内存 | 只跑佩戴检测、IMU、唤醒词 | 蜂窝 eDRX / PSM；Wi-Fi 关闭或低功耗 | 戴上、唤醒词、消息推送 | 待机功耗以整机实测为准 |
| S3 深睡 / 运输 | 关闭 | 只留实时时钟 | 关闭射频 | 长按或充电 | 存放数周仍有电（待定） |

### 5.2 技术要点

- **协处理器常驻**：佩戴检测、抬头动作、唤醒词、时钟和手表模式都在协处理器上，主处理器不醒也能判断“要不要醒”。
- **分电源域**：显示、解码、追踪摄像头、Wi-Fi、蜂窝分别断电。
- **会话保持**：串流服务端保留会话和最后一帧；眼镜醒来先显示缓存帧，再等新关键帧。
- **蜂窝节能**：依赖模组和运营商对 eDRX / PSM 的支持。公开论坛中已有用户反映某 RedCap 模组未进入 eDRX、休眠电流偏高，且厂商未公布 eDRX 电流【公开资料·用户反馈，未经本项目复现】[S23](sources.md#s23)。**机身蜂窝是待机功耗的最大风险，选型前必须实测休眠电流。**
- **系统策略**：自研串流服务须加入后台白名单，避免熄屏断网或后台服务被杀；验收必须覆盖这一点。

### 6.3 蜂窝候选（按“满足串流最低要求”选型）

需求方确认：机身蜂窝的最低要求是**满足串流最低要求**。

【项目判断】串流最低网络要求（设计目标，需按实际编码参数实测修正）：

| 场景 | 下行持续 | 上行持续 | 时延 | 说明 |
| --- | --- | --- | --- | --- |
| 云串流（1080p60，H.265 / AV1） | ≥ 30 Mbps | ≥ 2 Mbps（姿态与控制） | RTT p95 ≤ 50 ms | 头动由本地重投影承担，网络时延只影响内容响应 |
| 视频通话 / 会议（1080p30 上行） | ≥ 5 Mbps | ≥ 5 Mbps | RTT p95 ≤ 100 ms | 弱网降分辨率 |
| 串流 + 通话并发 | ≥ 35 Mbps | ≥ 8 Mbps | 同上 | 最重负载 |

据此：**机身蜂窝最低按 5G RedCap 选型**（公开峰值下行约 220 Mbps、上行约 120 Mbps，见下表），峰值有余量，但**持续速率、上行和时延必须在强弱信号下实测**；LTE Cat4 只在实测持续速率满足上表时作为备选。

| 位置 | 候选 | 已核实的公开信息 | 判断 |
| --- | --- | --- | --- |
| 机身（最低档） | Snapdragon X35（RedCap） | 高通称其为最低功耗芯片，目标含可穿戴与 XR 眼镜；下行峰值约 220 Mbps；5G PowerSave Gen 4。[S22](sources.md#s22) | 带宽足够独立上网与中等码率云串流；**首选评估**。 |
| 机身 | Quectel RG255C 系列（RedCap 模组） | R17 RedCap，5G SA，下行约 223 Mbps、上行约 123 Mbps；列出可穿戴应用。[S23](sources.md#s23) | 便于原型；有 eDRX 不生效、休眠电流偏高的用户反馈，需实测。 |
| 机身 | LTE Cat4 级（如 W527 自带） | 见 [S1](sources.md#s1) | RedCap 网络覆盖或模组不成熟时的备选。 |
| 线控模块 | 全功能 5G 模组 | — | 高码率云串流与长时间户外；靠模块大电池承担功耗。 |

## 7 关键取舍

| 取舍 | 选择 | 原因 | 代价 |
| --- | --- | --- | --- |
| 依赖手机 vs 依赖网络 | **依赖网络**，机身自带蜂窝 + Wi-Fi | 不带手机也是全功能 | 机身多一套射频，重量、功耗、认证成本上升 |
| 机身蜂窝档位 | 满足串流最低要求，最低按 RedCap | 待机与发热可控，带宽满足最低串流与通话 | 高码率云串流靠线控模块全功能 5G |
| 默认有线 vs 无线 | **默认无线** | 佩戴自由，不依赖线和手机 | 机身电池、散热压力最大 |
| 离线内容上传 | 接口 + 用户选择，默认不上传 | 隐私与灵活性 | 用户需在首次使用时做选择 |
| 断网能力 | 只保留手表级功能 | 功能边界清楚，续航最好 | 断网时无串流、无空间交互、无 AI |
| 单处理器 vs 主 + 协处理器 | 主 + 协处理器 | 手表模式与待机不用唤醒主处理器 | 两套固件，摄像头和存储需共享方案 |
| 完整 VR vs AR 交互 | 6DoF 能力 + 光学透视 AR 交互 | 与真实画面交互是核心 | 不以 VR 游戏沉浸感为目标；光学透视亮度、视场受限 |
| 有线原始画面 vs 编码串流 | 两者都支持 | A1 体验最好，A2 兼容面最广 | 多一条 DP 接收路径 |
| 逐应用适配 vs 系统级虚拟显示器 | 系统级为主 | 一次接入覆盖所有普通软件 | 需维护各主机平台驱动；DRM 内容不可用 |

## 8 可行性结论与待验证事项

**有证据支持的部分**：PC → 头显开源串流（ALVR、WiVRn）、平面串流（Sunshine / Moonlight）、DP 有线眼镜加眼镜端稳定（XREAL One 系列）、Windows 虚拟显示驱动、面向分布式处理的眼镜芯片（AR2 Gen 1）、面向可穿戴的 RedCap 芯片与模组、带 ISP 与 H.264 的低功耗 MCU，都已公开存在。

**仍是设计目标的部分**：

1. 端到端延迟预算（第 3.5 节），尤其是蜂窝云串流的时延与抖动。
2. 6DoF 追踪、手势、空间锚定在轻量眼镜上的功耗与精度。
3. “全软件兼容”——按类别清单测通过率；DRM / 反作弊 / 安全窗口为已知边界。
4. 睡眠各级功耗、手表模式续航与唤醒时间（第 5.1 节）——机身蜂窝休眠电流要最先测。
5. 主处理器与协处理器共享摄像头、存储的方案，以及模式切换时间。
6. AR2 Gen 1 / AR1+ Gen 1 对非头部品牌的供货、BSP 与开发者文档可获得性。
7. 可采购的 DP 接收 + 重投影芯片方案。
8. 机身同时放蜂窝、Wi-Fi 7 天线时的射频共存、SAR 与认证；6 GHz 国内可用性。
9. 视频通话三种接入方式（V1–V3）在主流通话软件上的实测通过率；虚拟摄像头是否被各软件识别。
10. 默认无线形态下，“串流 + 视频通话 + 6DoF + 蜂窝上行”并发的续航与温升。
11. 机身蜂窝持续速率、上行和时延能否满足第 6.3 节的串流最低要求。

**第一版样机范围（需求方确认：完全版）**：有线（A1 / A2）、Wi-Fi、机身蜂窝三种连接，6DoF 交互，视频通话 V1–V3，手表模式与同步接口，分级睡眠，全部进入第一版样机。线控模块作为配件同步打样。

【项目判断】完全版样机工作量大，建议在样机前先做下面的“现成硬件验证”，降低返工风险。

**建议的第一步验证（不需要自研硬件）**：

1. 现成 DP 有线眼镜 + PC 虚拟显示驱动 + 开源串流软件：测延迟、画质与兼容清单通过率。
2. 现成 6DoF 一体机或开发套件：验证“虚拟屏锚定在真实桌面 + 手势操作”的交互是否满足需求。
3. RedCap 开发板：实测 eDRX / PSM 休眠电流与云串流时延。
4. STM32N6 一类开发板：验证手表模式的拍照、录像、录音功耗。
5. 现成眼镜 / 一体机摄像头作为电脑虚拟摄像头：在微信、腾讯会议、Teams、Zoom 上测 V1 通话通过率。

这五组数据决定完全版样机的芯片与结构选型。
