# 串流终端方向：Quest 级体验的 AR 眼镜版

**v0.2.1 方向稿 · 2026-11-03 · 来源核验日期 2026-11-03**

本页把“自研眼镜”的三个目标——**串流获得 Quest 级体验、通过投屏转化兼容尽量多的软件、强睡眠能力**——整理成一套可评审的技术路线，并结合公开芯片资料和 GitHub 开源项目做了优化。

> **证据边界**：本页区分三类内容——【公开资料】有来源链接的厂商或项目公开信息；【项目判断】本项目的推理与取舍；【设计目标】希望达到但尚未测量的指标。厂商宣传数字（如延迟、功耗）未经本项目复现，不能当作整机实测结果。本页不是冻结规格。

与 [开发需求](requirements.md) 的关系：需求文档面向“独立蜂窝 + 现场作业”的轻量眼镜；本页是另一条**串流终端**产品方向，两者共用“ARM 应用平台 + 自主软件 + 可维护 BSP”的边界。冲突时以需求文档的硬性边界为准。

## 0 一句话方案

**眼镜只做“显示 + 低延迟解码 + 本地重投影 + 网络”，重渲染交给外部主机（PC、手机、车机、云）；有线是体验上限，Wi-Fi 7 是日常，5G 是独立上网和远程兜底；所有软件通过“系统级虚拟显示器”接入，而不是逐个适配；5G 与大电池放进可拆的线控模块，眼镜本体负责快速睡眠和秒级唤醒。**

相对 v0.1 的主要优化：

| # | v0.1 | v0.2 优化 | 依据 |
| --- | --- | --- | --- |
| 1 | 有线只写“USB-C / 专用线” | 有线拆成两种：**DP Alt Mode 原始画面**（不编码，延迟最低）与 **USB 编码串流**（兼容没有视频输出的主机） | XREAL One 系列走 DP Alt Mode 并在眼镜端芯片做稳定与畸变校正【公开资料】[S20](sources.md#s20) |
| 2 | 只讲“低延迟解码” | 加入**眼镜端本地重投影**（按最新头部姿态修正画面），把头动延迟和网络延迟解耦 | AR2 Gen 1 的分布式处理即把感知与低延迟环节留在眼镜端【公开资料】[S17](sources.md#s17) |
| 3 | 5G 模组放眼镜里，与续航冲突 | **5G 与大电池放进可拆线控模块**，眼镜本体保留 Wi-Fi 7 / 蓝牙；不接模块时眼镜仍可用 | 5G 是功耗大户；RedCap 降低功耗但实测休眠电流仍需核实【公开资料】[S22](sources.md#s22)[S23](sources.md#s23) |
| 4 | “兼容所有软件”无具体路径 | 兼容分 **5 层**：系统级虚拟显示器为主，OpenXR、标准车机协议、语义转化、像素转化补充 | 之前的投屏研究结论 + 开源项目（见第 3 节） |
| 5 | 睡眠含义待确认 | 已确认为“低功耗待机 + 快速唤醒”，给出分级功耗设计 | 第 4 节 |

## 1 整体架构

```
              ┌──────────── 外部主机（重渲染）────────────┐
              │ PC / 笔记本 │ 手机 │ 车机 │ 云端 / 远程桌面 │
              │ 虚拟显示器驱动 + 编码器 + 串流服务（自研）  │
              └──────┬──────────────┬───────────────┬──────┘
          ① 有线 DP Alt / USB      ② Wi-Fi 7 / 6E      ③ 5G（经线控模块）
                     │              │               │
   ┌─────────────────▼──────────────▼───────────────▼──────────────┐
   │ 眼镜本体                                                       │
   │  • 视频入口：DP 接收 或 硬件解码（H.265 / AV1，视芯片）           │
   │  • 本地重投影：按最新 IMU 姿态修正画面（3DoF 起步，6DoF 可选）      │
   │  • 显示：双目 Micro-OLED / 光波导（按光学档位）                   │
   │  • 低功耗传感岛：IMU、佩戴检测、唤醒词 → 负责睡眠与唤醒             │
   │  • Wi-Fi 7 + 蓝牙；小电池（可单独短时工作）                        │
   └─────────────────────────────┬─────────────────────────────────┘
                                 │ USB-C（供电 + 数据 + 视频）
                   ┌─────────────▼─────────────┐
                   │ 可拆线控模块（扩展仓）       │
                   │ 5G 模组 + eSIM/SIM + 大电池 │
                   │ 可选：主机 USB-C 直通、存储   │
                   └───────────────────────────┘
```

【项目判断】这样分的理由：

- **体验**：画面质量与渲染能力由主机决定，眼镜只需把“最后几毫秒”做好（解码、重投影、显示）。
- **续航与散热**：5G 射频和大电池是重量、发热、功耗的主要来源，放到线控模块后，眼镜本体可以更轻；不需要独立上网时可以拔掉。
- **扩展性**：线控模块和主机都可以替换升级（换 5G 模组、换更大电池、换成纯直通线），眼镜本体不用重新设计。
- **代价**：多一根线、多一个模块；纯无线 5G 一体眼镜不是本路线的第一版目标（见第 6 节取舍）。

## 2 目标一：串流终端（Quest 级体验的眼镜版）

### 2.1 三种连接模式

| 模式 | 链路 | 眼镜端工作 | 体验定位 | 主要前提 |
| --- | --- | --- | --- | --- |
| **A1 有线原始画面** | USB-C DP Alt Mode | 接收显示信号 + 重投影 / 畸变校正，不解码 | 最低延迟、无压缩画质；“超强体验”上限 | 主机须支持 DP Alt Mode 视频输出 |
| **A2 有线编码串流** | USB 3.x 数据通道 | 硬件解码 + 重投影 | 接近 A1，兼容没有 DP 输出的手机或主机 | 主机能硬件编码；需要自研串流协议或复用开源方案 |
| **B 无线串流** | Wi-Fi 7 / 6E（5 GHz / 6 GHz） | 硬件解码 + 重投影 + 抗抖动 | 日常移动使用 | 主机有线接路由器或 Wi-Fi 直连；信道质量 |
| **C 蜂窝** | 5G（线控模块） | 独立上网；远程桌面 / 云串流 | 离开主机时的独立使用与兜底 | 运营商、套餐、上行带宽与时延 |

公开参照：

- Quest 2 使用的 XR2（第一代）平台规格可选配 X55 实现 5G，并非平台强制项；Quest 2 是否带 5G 未核实【公开资料】[S19](sources.md#s19)。
- PC → 一体机的开源无线串流已有成熟实现：ALVR（基于 SteamVR，需主机 GPU 硬件编码）与 WiVRn（OpenXR 应用串流）【公开资料】[S24](sources.md#s24)[S25](sources.md#s25)。平面应用串流可参考 Sunshine / Moonlight（H.264、HEVC、AV1，AV1 取决于主机 GPU）【公开资料】[S26](sources.md#s26)。

### 2.2 延迟预算（设计目标，待实测）

| 环节 | A1 有线原始 | A2 有线编码 | B Wi-Fi 7 | 说明 |
| --- | --- | --- | --- | --- |
| 主机渲染 + 采集 | 依应用 | 依应用 | 依应用 | 不计入眼镜预算 |
| 编码 | 无 | 目标 ≤ 5 ms | 目标 ≤ 5 ms | 低延迟模式：无 B 帧、切片编码、帧内刷新 |
| 传输 | 线路级 | 目标 ≤ 2 ms | 目标 ≤ 5 ms（p95） | AR2 宣称眼镜—主机 Wi-Fi 7 持续延迟 < 2 ms，为厂商数字【公开资料】[S17](sources.md#s17) |
| 解码 | 无 | 目标 ≤ 5 ms | 目标 ≤ 5 ms | 视芯片硬解能力 |
| 重投影 + 显示 | 目标 ≤ 5 ms | 目标 ≤ 5 ms | 目标 ≤ 5 ms | XREAL 宣称 X1 方案运动到光子约 3 ms（120 Hz），未见独立实测【公开资料】[S20](sources.md#s20) |
| **头动感知延迟** | 由重投影决定 | 由重投影决定 | 由重投影决定 | 重投影后，头动延迟与网络延迟解耦，这是“串流也能有好体验”的关键 |

【项目判断】以上数字只是**拆账用的设计目标**，必须用同一测试方法实测：高速相机或光电传感器测运动到光子；投屏延迟计时页测内容延迟（p50 / p95 各 30 个样本以上）；30 分钟连续运行看 p95 是否漂移、温度是否触发降频。

### 2.3 眼镜端能力要求（按优化后路线）

| 能力 | 要求 | 状态 |
| --- | --- | --- |
| 视频解码 | 硬件 H.265 必选；AV1 优先（同画质码率更低，利于 Wi-Fi 和 5G） | 依芯片核实 |
| DP 输入 | A1 模式需要 DP 接收与显示桥接；或采用自带 DP 输入的显示/空间计算芯片 | 待选型 |
| 本地重投影 | 3DoF 起步（IMU）；6DoF 需摄像头追踪，属 B 档空间 AR，单独报价 | 待选型 |
| 显示 | 双目，1080p 级每眼起步，90–120 Hz 优先；具体按光学方案 | 待选型 |
| 无线 | Wi-Fi 7 优先（6 GHz、低时延）；蓝牙 5.3 | AR1+ / AR2 平台公开支持 Wi-Fi 7【公开资料】[S17](sources.md#s17)[S18](sources.md#s18) |
| 5G | 放线控模块；RedCap 优先评估功耗，全功能 5G 评估峰值带宽 | 见第 5 节 |
| 扩展 | USB-C 供电、数据、视频三合一；线控模块可替换 | 方向明确 |

## 3 目标二：通过投屏转化算法兼容尽可能多的软件

### 3.1 “之前研究的特殊投屏算法”指什么

【项目判断】根据此前的投屏调研，本项目所说的“特殊投屏算法”是以下组合，而不是某一种编码格式：

1. **主机侧渲染 + 视频 + 眼镜薄解码**：主机把内容画到一块虚拟画布，硬件编码后推给眼镜，眼镜只负责解码显示。
2. **串流纪律**：画面只保留最新一帧；同时只有一块数据在传；对端忙就丢帧而不是排队；回执逐项核对累计值；采集、编码、发送、解码、上屏分别计数，不把“已发送”当成“已显示”；断流时不显示花屏，等关键帧再恢复。
3. **ROI 局部放大**：在原始分辨率上先裁剪再缩放，让小屏也能看清局部内容。
4. **语义转化（主）+ 像素转化（兜底）**：能读到界面结构的应用，把内容重新排版成适合眼镜的卡片；读不到的再用画面捕获 + 裁剪 + 对比度适配。
5. **矢量与画面分开**：导航、字幕、状态等结构化数据单独传，由眼镜本地绘制，视频断开时仍能显示。

如果你指的是另一份具体资料，请指明后再替换本节。

### 3.2 优化后的兼容分层

“兼容所有软件”最有效的做法不是逐个适配应用，而是**在操作系统显示层接入**：主机系统把眼镜当成一台显示器，任何能在这台显示器上显示的软件就自然兼容。

| 层 | 方法 | 覆盖范围 | 开源参考 | 边界 |
| --- | --- | --- | --- | --- |
| **L0 系统级虚拟显示器（主路）** | Windows 用间接显示驱动（IddCx）创建虚拟显示器；Linux 用合成器 / Vulkan 层；Android 用 VirtualDisplay / 屏幕捕获；Mac 用系统扩展显示 | 所有桌面与普通应用，包括多窗口、多屏 | Windows 虚拟显示驱动开源项目 [S27](sources.md#s27)；Linux 眼镜虚拟屏 Breezy Desktop / XRLinuxDriver [S28](sources.md#s28) | DRM / HDCP 内容、安全窗口（如 FLAG_SECURE）不可捕获；驱动签名与系统版本 |
| **L1 OpenXR / VR 应用** | 主机运行 OpenXR 或 SteamVR 运行时，眼镜作为头显端 | VR / XR 应用 | ALVR、WiVRn [S24](sources.md#s24)[S25](sources.md#s25) | 需要 6DoF 才能完整体验；3DoF 只适合部分应用 |
| **L2 标准投屏 / 车机协议** | 眼镜作为接收端 | 手机生态的地图、音乐、语音等 | 此前已调研的车机接收端开源实现 | 协议授权、认证硬件和厂商条款须另行确认；本仓库不提供这类实现 |
| **L3 语义转化** | 读应用界面结构，重排为眼镜卡片 | 消息、文章、通知、列表类 | 无障碍界面树读取思路 | 需要用户授权；应用更新会使规则失效；不做未经确认的自动操作 |
| **L4 像素转化** | 画面捕获 + ROI + 单色或对比度适配 + 低码率编码 | L3 读不到的图片、小程序等 | 第 3.1 节串流纪律 | 低功耗或单色屏场景下的兜底；受安全窗口限制 |

【项目判断】兼容率应按“软件类别清单 + 实测通过率”衡量。建议首批测试清单：办公（浏览器、文档、视频会议）、开发（IDE、终端）、影音（本地播放器、受 DRM 保护的流媒体，预期部分失败）、游戏（Steam 平面游戏、OpenXR 游戏、反作弊游戏）、手机应用（消息、导航）。**DRM 保护内容、反作弊、仅限特定硬件的软件属于已知兼容边界**，不承诺可用，也不绕过。

### 3.3 自研串流协议的建议要点

- 会话握手带能力位（分辨率、刷新率、编码格式、重投影模式），并做时钟同步。
- 控制面与视频面分离：视频断开时，按键、模式切换、诊断仍可走控制通道。
- 视频面采用“最新帧优先 + 关键帧恢复 + 自适应码率”；Wi-Fi 与 5G 下按 p95 延迟动态降分辨率或帧率。
- 诊断以 JSON 记录各环节计数与时间戳，不保存画面内容。

## 4 目标三：强睡眠能力

### 4.1 含义（已确认）

需求方已于 2026-11-03 确认：“强大的睡眠能力”指 **极低功耗待机 + 快速唤醒 + 恢复原状态**，不是睡眠监测、助眠等健康功能。

### 4.2 分级功耗状态（设计目标）

| 状态 | 眼镜本体 | 线控 5G 模块 | 唤醒条件 | 设计目标 |
| --- | --- | --- | --- | --- |
| S0 使用中 | 显示、解码、Wi-Fi 全开 | 按需连接 | — | 由串流负载决定 |
| S1 浅睡（摘下 / 熄屏） | 显示关、解码器关，应用处理器挂起，串流会话保持 | 维持连接 | 戴上、触摸、按键 | 戴上后画面恢复 **≤ 1 s**（待实测） |
| S2 待机 | 应用处理器挂起到内存，只留低功耗传感岛与蓝牙低功耗广播 | eDRX / PSM 节能模式 | 戴上、唤醒词、消息推送 | 待机功耗数量级待定；以**整机实测**为准 |
| S3 深睡 / 运输 | 近关机，保留实时时钟 | 关闭射频 | 长按或充电 | 存放数周仍有电（待定） |

### 4.3 技术要点

- **低功耗传感岛**负责佩戴检测、IMU 抬头动作和唤醒词，主处理器不醒也能判断“要不要醒”。
- **分电源域**：显示、解码、Wi-Fi、5G 可以分别断电。
- **会话保持**：串流服务端保留会话和最后一帧，眼镜醒来后先显示缓存帧，再等新关键帧，减少“醒来黑屏”时间。
- **5G 节能**：依赖模组和运营商对 eDRX / PSM 的支持。公开论坛中已有用户反映某 RedCap 模组未进入 eDRX、休眠电流偏高，且厂商未公布 eDRX 电流【公开资料·用户反馈，未经本项目复现】[S23](sources.md#s23)。**选型前必须实测休眠电流。**
- **系统策略**：Android 类系统需把自研串流服务加入后台白名单，避免熄屏断网或后台服务被杀；此类问题在已有眼镜上已出现过，必须在验收中覆盖。

## 5 芯片组合优化

【项目判断】串流终端方向对芯片的要求与“独立蜂窝轻眼镜”不同：本地算力要求降低，**视频入口、重投影、Wi-Fi 时延和睡眠功耗**要求提高。建议按“眼镜本体 SoC + 线控 5G”组合评估。

### 5.1 眼镜本体候选

| 候选 | 已核实的公开信息 | 本方向的判断 |
| --- | --- | --- |
| **Snapdragon AR2 Gen 1** | 多芯片分布式架构（AR 处理器 + 协处理器 + 连接芯片），4 nm；Wi-Fi 7（FastConnect 7800），宣称眼镜—主机持续延迟 < 2 ms；设计上与手机或 PC 主机分担计算。[S17](sources.md#s17) | **最贴合“眼镜只做最后几毫秒、主机扛渲染”的思路**，优先询价。无蜂窝；内存、显示规格和开发者可获得的 BSP 未见公开资料，需询证。 |
| **Snapdragon AR1+ Gen 1** | 2025 年发布；Wi-Fi 7、蓝牙 5.3；单目或双目，最高每眼 1280×1280 @ 60 Hz；双 ISP。[S18](sources.md#s18) | 适合“轻串流 + 端侧 AI”。60 Hz 上限对强体验偏低；无蜂窝。 |
| **Snapdragon XR2 Gen 2 / XR2+ Gen 2** | XR2+ Gen 2 公开每眼最高 4.3K、Wi-Fi 7、全彩透视 12 ms。[S21](sources.md#s21) | 头显级算力与功耗，适合做**参考样机或主机端**，不适合轻量眼镜本体。XR2+ Gen 2 的 AV1 解码未在公开资料中确认。 |
| **显示 / 空间计算专用芯片路线** | XREAL One 系列以自研 X1 芯片在眼镜端做姿态预测、显示稳定和畸变校正，USB-C DP Alt Mode 输入，宣称约 3 ms。[S20](sources.md#s20) | 证明 A1 有线原始画面 + 眼镜端重投影路线可行；X1 为厂商自用芯片，本项目需寻找可采购的同类 DP 接收 + 重投影方案。 |
| 需求文档中的 W527 / W5 系列 | 公开为 LTE、1080p30 编解码级别。[S1](sources.md#s1)[S2](sources.md#s2) | 适合独立蜂窝轻眼镜，**视频能力不足以支撑本方向的强串流体验**，不作为串流主芯片。 |

## 6 关键取舍

| 取舍 | 选择 | 原因 | 代价 |
| --- | --- | --- | --- |
| 本地强算力 vs 串流 | 串流为主 | 眼镜轻、凉、续航好；体验随主机升级 | 离开主机时体验下降，需要 5G 或本地轻应用兜底 |
| 5G 在眼镜里 vs 线控模块 | 线控模块 | 重量、发热、续航；模块可替换 | 多一根线；纯无线 5G 一体机不在第一版 |
| 有线原始画面 vs 编码串流 | 两者都支持 | A1 体验最好，A2 兼容面最广 | 硬件多一条 DP 接收路径，成本上升 |
| 逐应用适配 vs 系统级虚拟显示器 | 系统级为主 | 一次接入覆盖所有普通软件 | 需维护各主机平台驱动；DRM 内容不可用 |
| 3DoF vs 6DoF | 3DoF 起步 | 虚拟大屏与平面应用已够用；成本低 | VR 游戏体验受限；6DoF 作为 B 档另报 |

## 7 可行性结论与待验证事项

**有证据支持的部分**：PC → 头显的开源串流（ALVR、WiVRn）、平面游戏串流（Sunshine / Moonlight）、DP Alt Mode 眼镜加眼镜端稳定（XREAL One 系列）、Windows 虚拟显示驱动、面向分布式处理的眼镜芯片（AR2 Gen 1）和面向可穿戴的 RedCap 芯片与模组都已公开存在。

**仍是设计目标的部分**：

1. 端到端延迟预算（第 2.2 节）——需用本项目的测试方法实测。
2. “全软件兼容”——按类别清单测通过率；DRM / 反作弊 / 安全窗口为已知边界。
3. 睡眠各级功耗与唤醒时间（第 4.2 节，含义已确认为低功耗待机 + 快速唤醒）——需整机实测，5G 模组休眠电流尤其要先测。
4. AR2 Gen 1 / AR1+ Gen 1 对非头部品牌的供货、BSP 与开发者文档可获得性。
5. 可采购的 DP 接收 + 重投影芯片方案。
6. 线控模块与眼镜间 USB-C 同时承载视频、数据、供电的信号完整性与发热。
7. 头部佩戴条件下的 Wi-Fi 7 实际时延、6 GHz 在国内的可用频段及认证。

**建议的第一步验证（不需要自研硬件）**：用现成 DP Alt Mode 眼镜 + PC 虚拟显示驱动 + 开源串流软件，先测 A1 / B 两种模式的延迟、画质和兼容清单通过率；同时用 RedCap 开发板实测 eDRX / PSM 休眠电流。这两组数据决定是否值得进入自研芯片选型。
