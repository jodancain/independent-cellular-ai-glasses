# 技术路线：从现成验证到完全版样机

**v0.1.2 · 2026-11-05 · 对应 [串流终端方向](streaming-direction.md) v0.7.6 · 来源核验日期 2026-11-04**

需求方要求：价格先不管，先把技术路线定下来。本页回答四个问题：

1. 每个子系统选什么：主选、备选，以及什么情况下切换。
2. 硬件之间怎么连，软件栈怎么搭。
3. 分几个阶段做到完全版样机。
4. 哪些验证结果会改变路线。

> **证据边界**：沿用方案的三类标注：
> - 【公开资料】：有来源可查。
> - 【项目判断】：本项目的推理和取舍。
> - 【设计目标】：还没测量过的指标。
>
> 芯片能力以厂商公开资料为准。**开发者能不能拿到芯片、BSP 和文档，目前都没核实**，所以每个关键选型都配了备选和切换条件。本页不含价格、交期和采购承诺。
>
> **命名约定**：本页的阶段记作 **M0–M3**。方案第 5.3 节的续航方案仍记作 P1–P4，比如“P1 机身混合使用 8 小时”。两套编号不要混用。

## 0 路线一句话

**眼镜本体用四颗主芯片分工**（按方案第 1.1 节的脑、小脑、手、脚标出角色）：
- AR 级主 SoC（**小脑**，也承载脑的端侧意图入口）：负责联网全功能和 6DoF。
- 显示与重投影处理器（**小脑**）：负责有线直通和上屏；M1 评估是否扩展为带硬件解码的“视频与显示处理器”。
- RedCap 蜂窝（**脚**）：负责独立联网。
- 低功耗 MCU（**小脑常驻**，兼管**脚**的 BLE 与**耳朵、嘴巴**的音频前级）：负责手表模式、睡眠和电源管理；**常驻收 BLE，并做唤醒词 / 人声检测的音频前级**。A 案（STM32N657 + 小 BLE 芯片）会多一颗小芯片，B 案（BES2800BP）蓝牙在片内。

**光学**第一版完全版样机（M2）直接用光波导：主选几何反射式（阵列）光波导，光机在 LCoS 与全彩 microLED 之间由 M1 定案；视场以光机与波导组合定案，目标 30–50°。birdbath、自由曲面棱镜等其他方案**已放弃，不再考虑**。

**软件**以开放协议为中心：
- 主机侧：统一的串流服务；手机这只手跑 Mika 改造版，提供任务接口。
- 眼镜侧：AOSP 系统加自研空间合成器，含小脑调度器与看板描述渲染。
- MCU：跑 RTOS，常驻 BLE 与音频前级。
- 云端：提供可以自建的同构服务端。

```
                         ┌──────────────── 眼镜本体（默认无线，全功能）────────────────┐
  USB-C ─ DP Alt ───────►│ ① 显示与重投影处理器 ──► 显示开关 ──► 左右光波导 + 光机     │
  USB-C ─ USB ──────────►│        ▲ 姿态 / 解码帧（MIPI）     ▲ 低功耗显示（MCU）      │
                         │ ② 主 SoC：解码 / 6DoF / 手势 / 合成 / 通话 / Wi-Fi 7         │
  Wi-Fi 7 ◄────────────►│        │ PCIe 或 USB          │ SPI + 中断 GPIO              │
  5G RedCap ◄──────────►│ ③ RedCap 模组（X35）+ eSIM   ④ 低功耗 MCU（含外挂 PSRAM）  │
  BLE ◄────────────────►│        │                     │ 常驻 BLE：气泡 / 看板描述    │
  麦克风阵列 ───────────►│        │                     │ 麦克风阵列直连 MCU           │
  扬声器 / 蓝牙耳机 ◄────│        │                     │ 音频前级 + 防漏音            │
                         │ 传感器：2 追踪相机 + IMU · 1 主摄（MIPI 开关）              │
                         │ 2 眼动相机（预留）                                          │
                         │ 电池：两块，分置两侧耳后                                    │
                         └─────────────────────────────────────────────────────────────┘
```

【项目判断】为什么是四颗主芯片，而不是一颗大 SoC：

- **有线 A1 的体验上限不该被主 SoC 卡住。**
  - DP 原始画面直接进显示处理器，重投影后上屏，延迟最低。
  - 只用 3DoF 稳定时，主 SoC 可以休眠（见 1.2）。
  - XREAL 的做法相同：眼镜里是自研显示芯片 X1 / X1S，重计算放在外部【公开资料】[S20](sources.md#s20)[S44](sources.md#s44)。
- **睡眠和手表模式不该唤醒主 SoC。** 这两件事由 MCU 单独完成（方案第 2、5 节）。
- **MCU 也要常连 BLE，音频前级常驻。** 手机这只手的气泡 / 看板描述主要走 BLE，主 SoC 睡着时由 MCU 收；唤醒词与人声检测也留在 MCU，麦克风阵列可直接接 MCU（方案第 5.4、6.2 节，决定 #24）。
- **蜂窝单独成块。** AR 级 SoC 的公开资料里没有集成基带；独立模组可以先用评估板验证，以后也方便换芯片。

## 1 子系统选型：主选、备选与切换条件

### 1.1 主 SoC（联网全功能）

| 档位 | 候选 | 公开信息 | 用在哪里 |
| --- | --- | --- | --- |
| **主选** | Snapdragon AR2 Gen 1 | 为“眼镜端感知 + 主机分担计算”设计的多芯片平台，Wi-Fi 7 [S17](sources.md#s17) | 完全版样机的眼镜本体 |
| **有条件备选** | Snapdragon AR1+ Gen 1 | 单芯片；比 AR1 小约 26%、省电约 7%；可在端侧跑小模型；支持单目和双目 HUD 输出。**公开显示规格为每眼最高 1280×1280、60 Hz** [S18](sources.md#s18) | 只在同时满足两个条件时可用，见下方 |
| **开发参考** | Snapdragon Reality Elite（2026 年 6 月发布，接替 XR2+ Gen 2） | 面向一体机和**有线连接的计算盒**。GPU 比 XR2+ Gen 2 高约 60%，NPU 48 TOPS，UFS 4.0，2 路 USB 3.1，蓝牙 6.0（均为厂商宣称）[S43](sources.md#s43) | 自研板做出来前，用来开发软件、验证 6DoF 交互；也是线控模块“算力版”的候选（见 1.10） |

**AR1+ 当备选的两个条件**：
1. 显示处理器负责把画面放大到面板分辨率。
2. 显示处理器用重投影把 60 Hz 内容补到 90 Hz 以上上屏。

做不到这两点，AR1+ 就达不到完全版的显示要求。

**主 SoC 门禁**【项目判断】：下面三条要在 M1 结束前拿到供应商书面答复或实测结果，不满足就不能当主 SoC。

1. 能在**没有手机或 PC 时独立运行** AOSP 系统、6DoF 和云串流客户端。AR2 的设计前提是和主机分担计算，所以这一条要最先确认。
2. 支持 H.265 硬解。AV1 是加分项。
3. 能把解码帧以不低于串流内容的分辨率（云串流按 1080p60，方案第 6.3 节）送给显示处理器；最终上屏分辨率以所选光机为准（待定，M1 定案），刷新率 60 Hz 起、由显示处理器补帧到 90 Hz 以上（见 1.2）。AR1+ 公开的每眼 1280×1280 @ 60 Hz 是否等于它能送出的解码帧规格，以供应商答复为准（第 5 节第 1 题）。

**切换顺序**：
1. AR2 不满足门禁 → 换 AR1+，前提是上面两个条件成立。
2. AR1+ 也不行 → 公开资料里没找到满足完全版要求的眼镜级 SoC。剩下的办法是做成“眼镜 + Reality Elite 计算盒”，也就是 XREAL Aura 那种分体形态 [S44](sources.md#s44)。**这会改变需求方第 11 条决定（默认无线），需要重新确认。**

### 1.2 显示与重投影处理器（有线直通 + 上屏）

| 环节 | 主选 | 备选 | 说明 |
| --- | --- | --- | --- |
| DP 接收 | 龙迅 LT7911UXC 一类桥接芯片：Type-C / DP1.4a 输入，MIPI DSI / CSI 输出，带 DSC 解码 [S45](sources.md#s45) | 同类 DP 接收桥接芯片 | 把 A1 有线画面转成 MIPI |
| 重投影、畸变与色差校正、缩放、补帧 | **原型用 FPGA**：按最新姿态对整帧做扭曲，同时完成放大和 60 → 90 Hz 以上补帧 | 送进主 SoC 的显示管线处理（多一次搬运，延迟和功耗都更高；A1 时主 SoC 必须保持工作） | 公开参照：XREAL One 系列在眼镜端芯片做稳定和畸变校正，宣称约 3 ms [S20](sources.md#s20) |
| 量产形态 | 第二代决定（见第 3 节），用可采购的显示处理芯片或 ASIC | — | FPGA 只用于原型快速迭代 |

**数据通路**【项目判断】：

- **A1 有线原始画面**，分两档：
  - **A1-3DoF（省电）**：主 SoC 休眠，显示处理器直接读 IMU，只做旋转稳定。虚拟屏跟着头部朝向稳定住，但不会随身体平移。
  - **A1-6DoF**：主 SoC 运行 VIO，把 6DoF 姿态交给显示处理器。DP 传来的是二维画面，适合当作“空间中的一块平面虚拟屏”合成。对平面来说，平移重投影是精确的。如果 DP 传来的是 3D 内容，因为没有深度，平移只能近似，这类内容应改走 L1 OpenXR 串流。
- **A2 / B / C 编码串流**：主 SoC 解码，经 MIPI 交给显示处理器扭曲后上屏。扭曲始终放在离屏幕最近的一级做，保证头动感知延迟不受网络影响（方案第 3.5 节）。
- **手表模式**：MCU 通过**显示开关**直接驱动低刷新、局部点亮的显示，主 SoC 和显示处理器断电。这需要屏幕驱动支持低功耗模式，见第 5 节第 4 题。

**可选路线：由“显示与重投影处理器”扩展为“视频与显示处理器”（M1 评估，不直接定案）**

【项目判断】目标是把串流时的硬件解码、重投影和上屏都放到一颗专用的低功耗“视频与显示处理器”上，让主 SoC 在串流时降到低功耗网络态甚至休眠，只在 6DoF、AI、通话时唤醒。这样 GPU、视频解码和显示管线可以关闭；CPU 的网络部分能否也关闭，取决于收流协议栈放在哪里。

| 候选 | 公开信息 | 本项目判断（均未经核实是否满足本项目） |
| --- | --- | --- |
| **Hexagon Semi HX77** | 面向 AR 眼镜的低功耗显示处理器，基于芯原 Nano IP；可驱动双路独立 1080p 显示，支持 MIPI / LVDS / DP / eDP【公开资料】[S54](sources.md#s54) | 显示与双目输出规格最贴近眼镜；**公开资料未说明是否带 H.265 / AV1 硬件解码**，这是首要书面确认项。 |
| **Synaptics VS680** | 带 AV1 / HEVC / H.264 等硬解和 MIPI DSI 输出，但面向智能显示设备；功耗级别不明【公开资料】[S55](sources.md#s55) | 作为“带硬解的显示处理器”参照，**不作主选**；功耗和眼镜形态适配待核。 |
| **解码 IP 路线** | 芯原 VC9800D 支持 H.264 / H.265 / VVC / AV1 / AV2 等【公开资料】[S56](sources.md#s56)；Allegro DVT、Chips&Media 等也提供视频解码 IP | 可集成进自研显示处理器（原型 FPGA，量产 ASIC）；集成工作量、面积和 IP 授权另评。 |

**边界（必须写清）**：Wi-Fi / 蜂窝收流需要网络协议栈（QUIC / RTP 客户端），**解码器本身不能跑协议**。要么主 SoC 停在低功耗网络态负责收包，要么视频处理器自带小 CPU 并直连 Wi-Fi 芯片。因此“主 SoC 释放”的程度是：**GPU / 视频解码 / 显示管线可关闭**；CPU 网络部分是否也能关闭，取决于方案，列为 **M1 门禁**。

【项目判断】第一版样机不直接按这条路线定案：M2 的基线仍是主 SoC 解码、显示处理器重投影上屏。若 M1 找到带硬解、能直连 Wi-Fi 且功耗合适的方案，再在 M2 用整机实测确认功耗收益；届时“串流使用 ≤2.0 W”的预算有望下调（见第 4 节）。

### 1.3 光波导与光机

需求方 2026-11-04 决定：显示方案**只用光波导**，birdbath、自由曲面棱镜等其他方案**已放弃，不再考虑**；第一版完全版样机（M2）直接用光波导，不再把波导放到“第二代”。

| 档位 | 方案 | 公开参照 | 取舍 |
| --- | --- | --- | --- |
| **光波导主选** | **几何反射式（阵列）光波导**，候选 Lumus Z-30 系列：30° 视场、演示机 720×720、几何反射式；新一代更薄（最薄 0.8 mm）、约轻 30%，70° 宽视场原型未公布量产时间 | [S49](sources.md#s49)[S50](sources.md#s50) | 视场小于已放弃的 birdbath，虚拟屏面积变小；前框更轻更透，符合“佩戴无感” |
| **光波导备选** | 衍射式光波导 | 本仓库未收集来源，**待调研** | 主选受阻时备选；视场、亮度均匀性和光效待核实 |
| **光机主选** | **LCoS 或全彩 microLED，M1 定案** | LCoS：Meta Ray-Ban Display 采用 Lumus 光波导 + LCoS 光机【公开资料】[S51](sources.md#s51)；全彩 microLED：JBD Hummingbird 0.13 英寸、640×480、30° 视场可在 25–45° 定制、1.0 g、典型功耗约 260 mW【公开资料】[S53](sources.md#s53) | 两条路线都未定案，按入眼亮度、分辨率、功耗、重量四项切换 |
| **光机参照** | 高亮度小尺寸 micro-OLED | 索尼 0.44 英寸 1080p、最高 10000 尼特【公开资料】[S46](sources.md#s46) | 作为亮度参照，不作为 M2 主选 |

**显示目标**【设计目标】：双目光波导，视场 30–50°（以光机与波导组合定案）；分辨率以所选光机为准（待定，M1 定案）；入眼亮度目标约 4000 尼特以满足户外可读【公开资料】[S52](sources.md#s52)；刷新率 60 Hz 起，显示处理器可补帧到 90 Hz 以上（待光机确认）。

**光机切换条件**：出现以下任一情况，就在 LCoS 与全彩 microLED 之间切换：
- **入眼亮度**：达不到约 4000 尼特的户外可读目标；
- **分辨率**：不满足所选串流内容和虚拟屏可读性要求（具体数值 M1 定案）；
- **功耗**：超出第 1.9 节的整机功耗预算；
- **重量**：前框重量和鼻托受力超出第 6 组基线。

【项目判断】**代价**：光波导当前视场明显小于已放弃的 birdbath 方案，虚拟屏面积变小，“Quest 级大屏观影”体验会下降；好处是前框更轻、更透，更符合“佩戴无感”（决定 #18/#19）。这是需求方已接受的取舍。前框光学减重后，方案第 7 节的重量估算**不改数字**，最终以 M2 实测为准。

处理办法：用第 6 组测得的鼻托受力基线约束光波导前框的重量；M2 用光波导实物测鼻托受力（见第 3 节）。

### 1.4 蜂窝（机身）

| 档位 | 方案 | 依据 |
| --- | --- | --- |
| **原型主选** | Quectel RG255C-GL 模组，基于 Snapdragon X35 [S40](sources.md#s40) | 第 3 组的验证对象；模组形态便于快速集成 |
| **对照 / 备选** | RG255G-GL（和 RG255C 用同一块评估板）[S38](sources.md#s38)；LTE Cat4 级 | 只在 eDRX / PSM 不生效，或持续速率不达标时启用 |
| **第二代方向** | X35 芯片级设计（chip-down），或更小封装的 RedCap 模组 | 改变射频和认证，归入第二代 |
| **SIM** | eSIM 为主，M2 期间保留实体卡槽 | 方便插运营商测试卡 |

**切换条件**：第 3 组（G3）测得以下任一项不达标，就换对照模组：
- 持续速率或 RTT 不满足方案第 6.3 节；
- **模组本身**的休眠电流不可接受。

整机待机功耗归第 4 节的 G4 和 M2 整机测试判断。换模组后仍不达标，高带宽场景交给线控模块，机身蜂窝降为“消息 + 语音 + 低码率”档。**这会改变需求方第 9 条决定，需要重新确认。**

### 1.5 低功耗 MCU（手表模式与睡眠）

决定 #24 要求 MCU 侧常驻收 BLE，同时不丢掉已经论证的拍照、录像通路。因此 M1 **并行评估 A / B 两案**，不预先定案：

| 档位 | 方案 | 依据 |
| --- | --- | --- |
| **A 案** | STM32N657：Cortex-M55，4.2 MB 片上 SRAM，带 ISP 和 H.264 编码 [S12](sources.md#s12)；**外挂 PSRAM**；**外加一颗小 BLE 芯片** | 保留已论证的拍照、录像通路；STM32N657 无无线射频，必须外加 BLE；代价是多一颗芯片、多一份 BOM 与布板面积 |
| **B 案** | BES2800BP：双 M55 + 双 STAR-MC1，8.3 MB SRAM，Wi-Fi、蓝牙、DSI [S10](sources.md#s10) | 蓝牙在片内，省掉外加 BLE；音频强；**ISP / H.264 证据不完整**，手表模式拍录像需短时唤醒主 SoC |
| **共同备选** | 主 SoC 平台自带的低功耗岛（AR2 本身含协处理器 [S17](sources.md#s17)） | 只有它开放给自研程序、能单独驱动摄像头和显示时才用 |

【项目判断】**A/B 闸门**：主 SoC 睡眠时，BLE 送来的气泡 ≤0.1 s 上屏【设计目标】。两案都要过这条闸门；同时比较 A 案多一颗芯片的重量 / 成本，和 B 案拍录像唤醒主 SoC 的功耗代价。验证方法见验证计划第 4 组。

**框图口径**：四颗主芯片不变；A 案在框图里多画一颗小 BLE 芯片，写成“四颗主芯片 + 1 颗小 BLE”；B 案蓝牙画在 BES2800BP 片内。

【项目判断】**内存预算**：一帧 1080p YUV420 约 3.1 MB，片上 4.2 MB 放不下录像缓冲加参考帧，所以 A 案的录像缓冲必须放在外挂 PSRAM 里。WAMR 和 Lua 两个运行时按需加载，不同时常驻（验证计划第 4 组）。

**音频**：唤醒词与人声检测常驻 MCU；麦克风阵列能直接接 MCU，主 SoC 睡时也能听；扬声器防漏音、蓝牙耳机切换在 M1 一并验证。器件型号仍待选型，不写未核实的型号和指标。

**系统支持**：Zephyr 对所选 MCU 的支持程度列为选型门禁（第 5 节第 6 题），不满足就退回 FreeRTOS；B 案要单独确认 BES2800BP 的 Zephyr / FreeRTOS 支持。

### 1.6 芯片之间的连接（硬件接口）

| 连接 | 接口 | 用途 |
| --- | --- | --- |
| MCU ↔ 主 SoC | SPI（数据）+ 2–3 根 GPIO（唤醒、中断、复位） | 状态机命令；主 SoC 上报“可以睡了”；手表模式录制内容的搬运通道 |
| MCU → 电源 | I2C 控制 PMIC 和各路负载开关 | 各电源域通断 |
| 主摄 | MIPI CSI 二选一开关；I2C、时钟、复位、电源随开关一起切换，MCU 仲裁 | 同一时刻只给 MCU 或主 SoC 一方用 |
| 显示 | 显示开关：正常时接显示处理器，手表模式切到 MCU 的低速显示接口 | 手表模式下主 SoC 和显示处理器都可以断电 |
| 主 SoC ↔ 显示处理器 | MIPI（解码帧）+ SPI / I2C（控制、姿态） | 编码串流上屏 |
| IMU | 同时接显示处理器和主 SoC，或由显示处理器转发 | 重投影直接用最新 IMU 数据 |
| 主 SoC ↔ RedCap | PCIe 或 USB | 蜂窝数据 |
| MCU ↔ BLE（A 案） | UART / SPI + 中断 GPIO | 小 BLE 芯片常驻收手机的气泡 / 看板描述；主 SoC 睡时由 MCU 处理 |
| 麦克风阵列 | PDM / I2S 直连 MCU；需要时经 MCU 或开关转给主 SoC | 唤醒词与人声检测常驻 MCU；通话上行 |
| 扬声器 / 蓝牙耳机 | I2S 音频；蓝牙耳机走系统蓝牙（B 案用 BES2800BP，A 案确认小 BLE 芯片是否支持音频，不支持则由主 SoC 蓝牙承担） | 防漏音、耳机切换；具体由哪颗芯片出蓝牙音频，随 MCU A/B 案定 |
| 存储 | 主 SoC 挂 UFS / eMMC；MCU 另挂小容量 NAND 存手表模式录制，联网后经 SPI 交给主 SoC 同步 | 避免两颗芯片抢同一个文件系统 |

**取消独立显示处理器**的前提：主 SoC 有 DP 或 MIPI 输入通路，接得住 DP 桥接芯片；同时保留显示开关给 MCU。两条都满足才能从四颗主芯片减为三颗，否则 A1 和手表模式的显示通路都会断。

### 1.8 USB-C 与无线

本节和 1.4（蜂窝）、1.5（MCU 侧 BLE）合起来就是**脚**的硬件：有线 USB-C、Wi-Fi 7、蓝牙 / BLE、机身蜂窝与天线（方案决定 #25）。

**USB-C 各模式的通道分配**【项目判断】：

| 模式 | 高速通道 | 眼镜的角色 | 说明 |
| --- | --- | --- | --- |
| A1 有线原始 | 4 路 DP | DP 接收端 + USB 2.0 设备（UVC / UAC 通话）+ 受电 | 带宽按最终光机分辨率与刷新率核算（M1 定案），4 路 HBR3 为高分辨率双目留余量；是否需 DSC 也在此阶段核算。主机 DP 不支持 4 路时，改为 2 路 DP 加 DSC |
| A2 有线编码 | USB 3 | USB 设备（串流 + UVC / UAC）+ 受电 | 不走 DP |
| 接线控模块 | USB 3（视模块版本加 DP） | 受电；数据角色由模块决定 | 模块直通主机时，沿用上面两行之一 |
| 充电 | — | 受电 | 由 PD 协商 |

DP 输入只接收主机正常输出的画面。带 HDCP 保护的内容按方案第 4.2 节属于已知边界，不去绕过。

**无线**：
- **Wi-Fi 7**：用 AR2 / AR1+ 平台配套的连接芯片。6 GHz 在国内能不能用还要核实，用不了就按 5 GHz 160 MHz 设计。
- **蓝牙**：5.3 起，连接耳机、手柄、戒指。
- **射频共存**：蜂窝、Wi-Fi、蓝牙三套天线的布局、隔离度、灵敏度下降和 SAR，**在 M2 画板前做天线方案，M2 整机实测**，不留到认证阶段（第 5 节第 7 题）。

### 1.9 电源、电池与功耗预算

- **电池**：两块电芯，分置左右镜腿耳后段，左右重量差 ≤ 3 g。
- **电源域**：以下各部分分别可断电，由 MCU 控制：
  - 显示、显示处理器、主 SoC；
  - Wi-Fi、蜂窝；
  - 追踪相机、眼动相机（预留电源域）、主摄。
- **状态机**：S0、S0'、S1、S2、S3 由 MCU 统一调度（方案第 5.1 节）。
- **S1 浅睡的会话保持**：
  - 主 SoC 不完全挂起，而是停在低功耗活跃态：关屏、停解码、停追踪。
  - 串流控制连接由 Wi-Fi 芯片的网络卸载或保活机制维持，蜂窝下由模组维持。
  - 超过保活时间就断开；戴上后按“缓存帧 → 重连 → 关键帧”恢复。

**功耗预算**【设计目标】：把方案第 5.3 节 P1 剖面的假设逐行相加，下限约 4.5 Wh，上限约 8.3 Wh。S1 / S2 取 0.05–0.1 W（方案第 5.3 节已补列）。所以 5–7 Wh 的电池**只有在功耗落在假设区间的中下段时才够**。路线按下表给主 SoC 和整机定功耗预算：

| 剖面时段（时长） | 方案假设 | **路线功耗预算** | 电量 |
| --- | --- | --- | --- |
| 串流使用（1 h） | 1.5–3 W | ≤ 2.0 W | 2.0 Wh |
| 视频通话 / 会议（0.5 h） | 2.5–4 W | ≤ 3.0 W | 1.5 Wh |
| 6DoF 叠加交互（0.5 h） | 1.5–3 W | ≤ 2.0 W | 1.0 Wh |
| 轻度联网（3 h） | 0.3–0.5 W | ≤ 0.4 W | 1.2 Wh |
| 手表模式（1 h） | 0.05–0.1 W | ≤ 0.08 W | 0.08 Wh |
| S1 / S2（2 h） | — | ≤ 0.08 W | 0.16 Wh |
| **合计** | 约 4.5–8.3 Wh | — | **约 5.9 Wh** |

【项目判断】按这份预算，7 Wh 电池约有 15% 余量。实测超出预算时：
1. 先压功耗：降低刷新率和追踪帧率，调整蜂窝策略。
2. 仍然不够，就按需求方第 19 条“续航为主”把电池加到 8–10 Wh，全部放在耳后。这会增加约 10–15 g 重量，算法按约 200–250 Wh/kg 推算。

这一步不需要重新确认决定，但重量会进一步上升，见第 6 节的重量更新。

**看板态（新增，决定 #24）**：

- **只看板**：主 SoC 只做“按描述画卡片 + 重投影”，降刷新率、关解码、关追踪；显示仍走显示处理器 / 光波导。
- **只有气泡**：走 MCU 现有低速显示通路，主 SoC 可睡；BLE 由 MCU 常驻接收。
- **看板 + 气泡**：主 SoC 进看板态，MCU 保持 BLE 常驻，按 1 主 + 2 气泡规则合成。
- 上面这张功耗预算表**不改**；看板态单列，做成 M1 测试项（验证计划第 4 组），实测后再回填。

**新使用剖面（待 M1 定案）**：决定 #24 要求按新的使用方式重算，新增看板（预计时长最多）、实时拍照 / 识别（摄像头上行 + ISP）、气泡待机，调低串流 / 视频时长。具体时长和功耗写“待定（M1 定案）”，不先填数字。

| 使用状态 | 相对已冻结剖面 | 预计时长 | 平均功耗 | 说明 |
| --- | --- | --- | --- | --- |
| 看板（含气泡） | 新增，预计时长最多 | 待定（M1 定案） | 待定（M1 定案） | 手发描述、小脑光栅化；只看板走看板态 |
| 实时拍照 / 识别 | 新增 | 待定（M1 定案） | 待定（M1 定案） | 摄像头上行 + ISP；短时 |
| 气泡待机 | 新增 | 待定（M1 定案） | 待定（M1 定案） | 仅 MCU + 低速显示 |
| 串流 / 视频 | 调低 | 待定（M1 定案） | 待定（M1 定案）；旧预算上限仅作对照 | 视频不再是主要场景 |
| 视频通话、6DoF、轻度联网、手表模式、S1 / S2 | 保留 | 待定（M1 定案） | 待定（M1 定案） | 口径同旧剖面 |

【项目判断】**替代关系**：新剖面用于 M1 的功耗预算和 MCU A/B 评估；M1 定案前，旧剖面仍是续航验收口径。**5–7 Wh 是否够，要按决定 #19 用新剖面重新核算**，结论待 M1；不足时先压功耗，再按第 1.9 节旧规则把电池加到 8–10 Wh，不直接放宽 8 小时指标。

### 2.2 四类主机怎么接入、怎么通话

【项目判断】不是每类主机都能走每种方式，M1 的出口按下表逐格判断：

| 主机 | 画面接入 | 通话主路 | 说明 |
| --- | --- | --- | --- |
| PC / 笔记本 | L0 虚拟显示 + 串流，或 A1 有线 | **V1**（眼镜注册为摄像头和麦克风） | V1 覆盖面最大 |
| 手机 | 手机这只手：Mika 改造版（任务接口 · 看板生成 · 虚拟显示 + 编码），或 A1 有线 | **V2 / V3** | 手机上的通话软件一般不能选外接虚拟摄像头（验证计划第 5 组）；iOS 能力另行评估 |

### 2.3 开放协议（M1 阶段先冻结 v0）

| 协议 | 内容 | 传输 |
| --- | --- | --- |
| 串流会话（控制面） | 能力位握手；主机发现与切换，顺序为有线 > 局域网 > 云 | QUIC 可靠流，或 TCP + TLS |
| 视频面 | 最新帧优先、关键帧恢复、自适应码率、逐环节计数 | **不可靠传输**：QUIC DATAGRAM（RFC 9221）或 RTP / UDP，按帧可选前向纠错，不做整帧重传。**不能用 QUIC 的普通流**：普通流可靠有序，会被队头阻塞，违背“最新帧优先” |
| 姿态上行 | 6DoF 姿态 + 时间戳，供主机做预测渲染 | 和视频面一样走不可靠传输，单独作为一个高频小包通道 |
| 时钟同步 | 主机与眼镜时钟对齐，用于姿态预测和延迟统计 | 类似 NTP 的往返测量，持续估算偏差；精度目标在 M1 用实测确定 |
| 矢量通道 | 导航、字幕、状态、L3 看板，由眼镜本地绘制 | 控制面 |
| 看板描述 | 手 → 小脑的结构化描述：文字、头像、按钮、布局，KB 级；字段在 v0 冻结 | BLE 控制面；大描述走 Wi-Fi |
| 手协议 v0 | 发目标、查状态、等待、回答、引导、取消；任务来源、权限和确认边界 | BLE / 局域网 / WSS |
| 同步接口 | 上传目标插件（方案第 2.4 节） | HTTPS |
| 小程序分发 | 签名包、权限清单 | HTTPS |

【项目判断】
- 控制面和视频面至少要分开拥塞控制，避免视频突发把按键和模式切换拖慢。
- 协议规范和参考实现一起公开（方案第 4.4 节）。官方云和自建服务端用同一份规范，用一致性测试套件验证第三方实现。

**看板描述 v0 草案要点**（M1 冻结）：

- 版本、看板 ID、来源手、更新时间、过期时间。
- 元素类型：文本、图片引用、按钮、列表、进度 / 状态；每项带布局约束（位置、大小、对齐）。
- 更新方式：整版替换或增量更新；默认只传变化部分。
- 兜底：描述表达不了时带一张图片引用，由手直接发图；不默认传整屏像素。
- 安全页标记：付款、密码等页面只发“黑屏 + 提示到手机处理”的标记，不发画面内容。

**手协议 v0 草案要点**（M1 冻结）：

- 任务 ID、目标、发起方、能力位、超时和取消。
- 状态机：排队 → 执行 → 等待确认 / 等待回答 → 完成 / 失败 / 取消；查询状态和等待结果分开。
- 确认请求：远程发起的任务只能请求确认，不能代替用户批准付款和密码；发消息、发文件、删除等不可逆动作要在眼镜上确认。
- 审计：记录任务来源、执行手、确认结果和时间戳；不记录画面内容。

## 3 阶段路线

| 阶段 | 做什么 | 进入条件 | 完成标准（出口） |
| --- | --- | --- | --- |
| **M0 现成硬件验证**（进行中） | [验证计划](validation-plan.md) 第 1–6 组；第 1、3、6 组先做 | — | G1–G6 都有结论；方案里的关键【设计目标】有了【实测】基线 |
| **M1 桌面功能样机** | 用开发板在桌面拼出**全链路**：<br>• 参考平台（Reality Elite / XR2 Gen 2 开发套件或头显）跑眼镜侧软件<br>• DP 桥接评估板 + FPGA 板跑重投影，接现成光波导模组 / 光机评估板<br>• RedCap 评估板<br>• STM32N6 / BES2800 开发板按 A/B 两案跑手表模式、状态机、BLE 气泡与唤醒词<br>• 板间按 1.6 的接口连起来 | 第 1、3 组的基线已建立，且没有阻断项。G1 的端到端延迟阈值和 G2 的阈值，在基线出来后再定 | • 按 2.2 的表逐格跑通<br>• A1（两档）、A2、B、C 四种连接都跑通<br>• 虚拟形象用语音 + 头部姿态驱动跑通；眼动接口预留核对<br>• 手表模式与 S0–S3 切换跑通，含 S1 会话保持<br>• 看板态、BLE 气泡 ≤0.1 s、主 SoC 睡眠时唤醒词有结论<br>• 各电源域功耗分别实测<br>• 协议 v0 冻结，含看板描述与手协议<br>• 主 SoC 门禁有结论，定案<br>• MCU A/B 案定案<br>• 天线方案完成 |
| **M2 完全版样机（EVT）** | 自研主板 + 柔性板，装进眼镜形态的结构；光学用**光波导**（主选几何反射式，光机 M1 定案）。需求方确认第一版就是完全版：有线、Wi-Fi、蜂窝、6DoF、通话、虚拟形象、手表模式、分级睡眠全部包含 | M1 出口全部达成；G6 给出重量分配基线 | • 全部功能在眼镜形态上可用<br>• **P1 续航剖面整机实测 8 小时**，这才是续航的最终闸门<br>• 光波导实物的鼻托受力与对标产品对比<br>• 并发主场景（串流 + 通话 + 6DoF + 蜂窝上行）的温升<br>• 射频共存与 SAR 摸底 |
| **M3 优化样机（DVT）** | 只在 M2 冻结的架构内优化功耗、重量和散热；做认证预测试（无线电型号核准、进网、SAR、电池安全） | M2 暴露的问题都有对策 | P1 剖面 8 小时达标；佩戴无感达标；认证预测试没有阻断项 |
| **第二代（另起 EVT）** | 改架构的项目：**更大视场光波导**、蜂窝芯片级设计、用显示处理芯片或 ASIC 替代 FPGA、可能取消独立显示处理器 | M3 完成 | 另立计划 |

【项目判断】
- **M1 是本路线新加的一步。** 完全版样机牵涉四颗主芯片（A 案另加一颗 BLE）、三种连接、四类主机，直接画板风险太大。先在桌面把软件、协议和芯片间接口跑通，M2 画板时就只剩硬件集成问题。M1 可以和 M0 部分重叠：第 1 组搭好的主机侧环境直接进入 M1。
- **改架构的项目不放进 M3。** 更大视场光波导、蜂窝芯片级设计和去掉 FPGA，都会改变光学、射频或显示电子。放在 DVT 里做，等于把 EVT 和认证推倒重来，所以单独归为第二代。

## 4 结果如何改变路线

| 结果 | 路线变化 | 是否改变需求方决定 |
| --- | --- | --- |
| G1 有线延迟达标，Wi-Fi 不达标 | 先调编码参数和信道再测；仍不达标，就把游戏和空间应用优先放到有线 | **改变第 11 条（默认无线全功能）的体验范围，需要重新确认** |
| G2 锚定或手势不达标 | 先提高追踪相机规格或算法；仍不达标，再考虑把 6DoF 简化为“虚拟屏锚定 + 简化手势” | **简化会改变第 5 条，需要重新确认** |
| G3 RedCap 不达标 | 换对照模组；仍不达标，高带宽交给线控模块 | **改变第 9 条，需要重新确认** |
| G4（暂定）：子系统功耗代入后超出 1.9 的预算 | 先压功耗，再按续航优先把电池加到 8–10 Wh。第 3、4 组只测蜂窝和 MCU，所以 G4 只是早期预警，最终以 M2 整机 8 小时实测为准 | 不改变（第 19 条已定续航优先），但重量上升 |
| G5 部分通话软件 V1 不通过 | 按 2.2 的表改走 V2 / V3 | 不改变第 12 条，前提是每个软件至少有一条路径；都不通的列入清单，**向需求方说明** |
| G6 配重样架基线 | G6 只验证“重量后移”的假设；光波导前框是否超标在 M2 用实物测。超标就前框换轻材料或调整重量分配 | 不改变 |
| 若找到带硬解的视频与显示处理器（HX77 等） | 串流时主 SoC 降为低功耗；功耗预算中“串流使用 ≤2.0 W”有望下调，M2 实测确认 | 不改变（第 19 条续航优先）；下调幅度以实测为准 |
| 后续启用眼动 | 按后续版本选配立项，启用已预留的结构空间、走线、连接器、MIPI 接口与电源域；软件补眼动驱动与注视交互 | 不改变当前版本决定（第 20 条），启用时按后续版本重新确认范围 |
| 主 SoC 门禁不通过 | 按 1.1 的顺序切换；走到“计算盒”形态时 | **改变第 11 条，需要重新确认** |

## 6 与方案的关系，以及本次更新

- 本页把方案第 6 节（芯片组合）和第 9 节（第一版样机）落成具体路线。选型结论回写方案时仍标【项目判断】，等 M1 定案后再改。
- **眼动**：需求方 2026-11-03 决定当前版本只做预留、不上；本页第 0 节框图与第 1.7、1.9、2.1、3、4 节已同步，虚拟形象改用语音 + 头部姿态驱动。
- **光学**：需求方 2026-11-04 决定显示方案只用光波导，birdbath、自由曲面棱镜等**已放弃，不再考虑**；M2 直接用光波导。本页第 0、1.2、1.3、3、4、5 节已同步，原“第二代波导减重”改为“更大视场光波导”。
- **续航**：方案第 5.3 节原来写的剖面“约需 4–6 Wh”，逐行相加的结果其实是约 4.5–8.3 Wh，方案第 5.3 节已改正。本页用 1.9 的功耗预算把需求收在约 5.9 Wh，电池仍按 5–7 Wh 设计。
- **脑、小脑、手（决定 #22–#24，2026-11-04）**：本页第 0、1.5、1.6、1.9、2.1、2.3、3 节已同步。四芯片骨架不变；A 案在 MCU 外多一颗小 BLE 芯片，B 案改用 BES2800BP；新增看板态与新使用剖面；视频不再是主要场景，HW-DP-06 降为 P2 / M1 次要评估项（见设计开发要求）。
- **脑、小脑、手、脚（决定 #25，2026-11-05）**：本页第 0、1.8、2.1 节标出各部件的角色；连接（蜂窝、Wi-Fi、BLE、USB-C）统一称为脚。选型与数字不改。
- **重量**【项目估算】：

  - M2 前做逐项重量预算。
