# 设计开发要求

**v0.1 · 2026-11-03 · 依据 方案 v0.7.2、技术路线 v0.1**

本文件把 [方案](streaming-direction.md) v0.7.2 第 0.1 节需求方已确认的 19 条决定、[技术路线](technical-roadmap.md) v0.1 的四芯片结构、接口、功耗预算、软件栈、开放协议与 M0–M3 阶段，以及 [验证计划](validation-plan.md) 的闸门 G1–G6，转写为可验收的设计开发要求。除明确标注的公开参照外，不引入仓库外事实；不新增产品需求，不补造数字。

## 0 证据边界与读法

### 0.1 依据与范围

- 产品需求依据只来自上述三份文档；公开边界与仓库约束按任务要求执行（SEC-08、DEV-13）。[系统架构图](system-architecture.md) v0.1 与本文件同时发布，图中的接口、通路和状态机与本文件 HW / PWR / PROT / CALL 各节对应；两者冲突时以本文件和技术路线为准。
- 本文件覆盖完全版样机（M2）及之前的开发要求；波导减重、蜂窝 chip-down、ASIC 替代 FPGA、取消独立显示处理器等属于第二代架构，不在 v0.1 验收范围。
- M1 可在桌面功能样机上验证；M2 在眼镜形态复验；M3 只在 M2 冻结架构内优化功耗、重量和散热，并做认证预测试。

### 0.2 证据边界

文中所有数值均为【设计目标】，**未实测**。厂商公开数字（包括芯片峰值、延迟、功耗宣传值）未经本项目复现，不能当作整机实测结果，也不能替代验收。源文档未给数值、明确写“待定”或写“首轮测基线后确定”的，本文件统一写「待定（M1 定案）」；M1 用验证计划基线定案，定案前不得写成已冻结指标。源文档之间的冲突不在本文件中自行裁决，另在交付说明中列出。

本文件不是冻结规格、性能承诺、采购订单或交期承诺。开发板、商用眼镜和模组评估板的结果只能说明趋势，不能直接当作目标整机数据。

### 0.3 三个编号体系不要混用

| 记号 | 含义 | 用在哪里 |
| --- | --- | --- |
| P0 | 必须；完全版样机必须具备，或放行前必须完成的交付/流程要求 | 本文件“优先级”列 |
| P1 | 应该 | 本文件“优先级”列 |
| P2 | 可选 | 本文件“优先级”列 |
| P1–P4 | 续航方案：P1 机身混合使用、P2 镜腿热插拔电池、P3 线控模块/口袋电池、P4 主机供电 | 方案 §5.3；本文件只在引用续航方案时写“续航 P1”等 |
| M0–M3 | 阶段：M0 现成硬件验证、M1 桌面功能样机、M2 完全版样机（EVT）、M3 优化样机（DVT） | 本文件“阶段”列 |

**优先级 P1 只表示“应该”，与续航方案 P1 无关。** 引用续航方案时必须带“续航”二字，避免与优先级混淆。阶段列只写要求最晚满足的 M1、M2 或 M3。

### 0.4 来源与验证写法

- 「决定#n」指方案 §0.1 的 19 条决定；「方案§x」指 [方案](streaming-direction.md)；「路线§x」指 [技术路线](technical-roadmap.md)；「验证计划 Gx」或「验证计划第 x 组」指 [验证计划](validation-plan.md)。
- 验证方法只使用四类：**测试**（仪器/台架/整机测量）、**分析**（计算、预算、架构核对）、**检查**（审阅文档、配置、清单、供应商答复）、**演示**（在样机上执行可观察的功能流程）。
- 延迟类测试按验证计划 §0.3：p95 用 nearest-rank，每组至少 30 个有效样本；网络类 RTT 至少 300 个样本。测试条件、设备和版本必须记录，原始数据不进公开仓库。

### 0.5 公开边界

本文件只写可公开技术信息，不写公司内部信息、价格、供应商联系人或密钥。测试原始视频、录音、日志、账号、真实设备序列号、SIM 卡号、IMSI/IMEI 和受试者个人信息按验证计划 §0.1 脱敏，不进入公开仓库。

## 16 需求变更规则

### 16.1 变更分级

| 级别 | 触发条件 | 确认要求 | 记录 |
| --- | --- | --- | --- |
| A 类：触及需求方决定 | 改变方案 §0.1 的 19 条决定之一 | **必须由需求方重新确认**；未确认前不得按新方向排期、采购或验收 | 记录确认日期、确认人、变更理由和影响范围 |
| B 类：改变要求但不触及 19 条决定 | 改变 P0/P1/P2、关键数字、验证方法、阶段或验收闸门 | 项目技术负责人评审；涉及对外交付的，需求方知会 | 版本号 +0.1，更新追溯表和验证计划 |
| C 类：文字/来源/编号修订 | 不改变要求含义和验收口径 | 编辑修订 | 记录修订说明，不改变编号 |

### 16.2 变更流程

1. 提变更单：写原要求编号、拟改内容、理由、依据、影响范围（硬件/软件/结构/验证/认证）、验证代价、是否触及 19 条决定。
2. 判定级别：A 类先停，交需求方重新确认；B 类交技术评审；C 类直接编辑。
3. 更新文件：修改要求表、关键数字索引和追溯表；版本行注明新版本和依据。
4. 通知与回读：通知硬件、软件、结构、验证和认证负责人；修改后回读确认没有遗漏旧编号。

**实测不达标不等于要求自动改变。** 先记录偏差、原因和候选对策，再按上表走变更；不得在验证报告里直接放宽指标。
